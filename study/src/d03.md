## 1. 為什麼 IoT 需要輕量協定 {{考科一 2.2｜指引 p.4-40}}
連上網（Wi-Fi、5G、LoRa）之後，下一個問題是「**數據如何被封裝與交換**」。HTTP 為網頁設計，在硬體資源受限、網路不穩的 IoT 環境顯得笨重，因此出現 MQTT、CoAP 等輕量協定。

## 2. MQTT、HTTP、CoAP 三者比較 {{考科一 2.2｜指引 p.4-40～4-42}}
| | MQTT | HTTP/HTTPS | CoAP |
|---|---|---|---|
| 底層 | **TCP**/IP | TCP/IP | **UDP** |
| 通訊模式 | **發布/訂閱（Pub/Sub）**＋Broker | 請求/回應（Req/Res） | 請求/回應，支援 REST（GET、POST、PUT、DELETE） |
| 標頭 | 極小（最小 **2 Bytes**） | 大（數百 Bytes） | 小（**4 Bytes**） |
| 即時性 | 高（主動推播） | 低（需輪詢 Polling） | 中 |
| 可靠性 | **QoS 機制** | 依賴 TCP 重傳 | 內建確認機制 |
| 適用 | 大規模感測網、即時控制、行動裝置 | 韌體更新、影像傳輸、Web 介面 | 極低功耗感測器、NB-IoT 設備、智慧電表 |

- MQTT：IBM 於 **1999 年**為監控輸油管線開發，強調低頻寬、低硬體需求、網路不穩時的可靠性。
- HTTP：伺服器**無法主動推播**給裝置（除非 WebSocket 或 Long-polling）。
- CoAP：「輕量版 HTTP」；走 UDP **不需維持長連線（Keep-alive）**，喚醒時間更短。**CoAP 沒有 QUERY 這種請求方法**（p.4-45）。

{{考科一 2.2｜指引 p.4-43～4-46 練習題}} **WebSocket**：建立後可**雙向即時通訊**，適合視訊通話、即時監看；指引練習題認為 HTTP 在 server 回應後會斷線，而 Socket、WebSocket、FTP 不會。

> **⚠️ 標註**：「HTTP 回應後即斷線」是 HTTP/1.0 的預設行為；HTTP/1.1 預設持久連線（keep-alive）。考試遇到此題型**依指引答 HTTP**。


:::check 考科一 2.2
某閘道器每季需要從伺服器下載一個約 2 MB 的韌體更新檔，同時也提供一個給工程師用瀏覽器查看設定的 Web 介面。依講義的 MQTT／HTTP／CoAP 比較表，這兩項需求最典型對應哪一種協定？
A. HTTP/HTTPS
B. CoAP
C. MQTT QoS 0
D. Modbus RTU
= A
> 比較表中 HTTP/HTTPS 的適用場景是「韌體更新、影像傳輸、Web 介面」；它標頭大、需輪詢，不適合高頻小量即時資料，但大型檔案與網頁正是它的強項。CoAP 適合極低功耗感測器；MQTT 適合大規模即時推播；Modbus RTU 是工業串列協定。
:::

## 3. 封裝與解封裝、網路五層 {{考科一 2.3｜指引 p.4-47～4-50}}
指引 4.3 節用 **TCP/IP 五層（含實體層）**說明：應用層、傳輸層、網際網路層、資料連結層、實體層。

- **封裝（Encapsulation）**：資料往下傳，**每一層加上自己的標頭（Header）**。
- **解封裝（Decapsulation）**：接收端往上傳，**逐層移除標頭**。
- 資料連結層把封包封成「**訊框（Frame）**」，以 **MAC 位址**定址，常見設備是**交換器**；實體層包含電纜、光纖、網路卡、**中繼器**。

以 Modbus 為例（p.4-50）：應用程式要讀保持暫存器 → 函式庫轉成 **Modbus PDU（功能碼＋資料欄位）** →
- **Modbus TCP**：加 **MBAP Header**，再經 TCP、IP 送出；
- **Modbus RTU/ASCII**：加**裝置位址＋錯誤檢查碼（CRC 或 LRC）**，成為串列訊框，經 **RS-232/RS-485** 傳輸。
接收端反向解封裝、驗證 CRC/LRC、解析 PDU 後執行，再用同樣流程回傳。

### TCP vs. UDP {{考科一 2.3｜指引 p.4-48、p.4-69～4-71}}
| | TCP | UDP |
|---|---|---|
| 連線 | **連接導向**（傳輸前三次握手） | **無連接** |
| 可靠性 | 保證按順序、完整到達 | 不保證可靠、順序、不重複 |
| 速度 | 較慢、開銷大 | 快、即時性高 |
| 適用 | 檔案、郵件、網頁請求；MQTT、Modbus TCP | 影音串流、即時應用；CoAP |

{{考科一 2.3｜指引 p.4-69～4-71 練習題}} 其他練習題常考：**LAN** 是小範圍（一棟或一組建築物）的網路；**IPv4** 由 4 組 0–255 的數字以「.」分隔（如 192.168.0.1）。

## 4. 為什麼工廠要從 Modbus 走向 OPC UA {{考科一 2.3｜指引 p.4-51}}
早期產線自動化低，傳統工控普遍用 **Modbus**：簡單可靠，但**設計時沒考慮資安**，沒有加密與身分驗證。現代製造要小批量、多樣化、安全的資料交換，因此導入 **OPC UA** 這類提供**加密、身分驗證與授權**的進階協定。

## 5. OPC UA {{考科一 2.3｜指引 p.4-51～4-56}}
由 **OPC 基金會（OPC Foundation）**開發，跨平台、開放、統一，被視為工業 4.0 關鍵標準。

主要特性：
1. **平台獨立**：不依賴特定 OS 或硬體，從嵌入式 MCU 到雲端都能實作（不是只限 Windows）。
2. **內建多層次安全**：認證、授權、資料完整性、加密通訊。
3. **可擴展的服務與資料模型（資訊模型）**。
4. 多語言實作：C++、C#、Java、Python。
5. **Client/Server 架構**：Server 通常在設備端，收集控制器與感測器資料並轉成標準格式；Client 向 Server 要資料。
6. 把各廠牌設備存取函式庫封裝在 OPC UA Server，形成**設備聯網閘道器平台**，對外提供統一存取方式。
7. 促進**水平與垂直整合**：設備 → MES → ERP 的無縫資料流。

**四種資料存取方式（必考）**：

| 方式 | 白話 | 例子 |
|---|---|---|
| 讀/寫 Read/Write | 主動讀變數或寫新值 | 讀產品重量；寫入新的進給率 |
| 資料變更通知 Data Change Notification | **訂閱變數**，值改變時伺服器通知 | 訂閱刀具壽命、機器溫度超過閾值 |
| 方法 Method | 遠端呼叫伺服器提供的方法 | 遠端觸發自動換刀程序 |
| 事件通知 Event Notification | **訂閱事件**，被動接收事件通知 | 緊急停機、機器手臂故障、系統日誌 |

{{考科一 2.3｜指引 p.5-26～5-27 練習題}} OPC UA 資訊模型（Information Model）中 **NodeId 不能重複**；指引練習題解析認為 OPC UA 對應到 **OSI 第 7 層（應用層）**。

> **⚠️ 易混淆**：「Data Change」訂閱的是**變數值的變化**；「Event」訂閱的是**事件（故障、警報）**。題目說「訂閱特定事件、被動接收通知」→ Event Notification。

## 6. MTConnect {{考科一 2.3｜指引 p.4-56～4-59}}
專為製造業（特別是**工具機**）設計的開放標準，定義一組**標準設備參數名稱**描述設備效能與即時狀態。三個關鍵字：**唯讀（Read-only，只讀不寫指令）、XML、HTTP**。

特性：開放源碼且**免授權費（royalty-free）**、可擴展（基於 XML）、互操作性、可讀性（XML 人與機器都好讀）。應用：生產監控、預測性維護、數據分析與優化。

**四元素資料流**：

| 元素 | 角色 |
|---|---|
| 設備 Device | 實體機器：CNC、機器人、檢測儀；產生運行狀態、主軸轉速、進給速度等參數 |
| 適配器 Adapter | **存取設備資料並轉成 XML**；不同控制器用不同函式庫（如發那科用 FOCAS） |
| 代理器 Agent | **核心**；整合一或多個 Adapter 的資料，以標準 XML 儲存，透過 **HTTP RESTful API** 提供；負責緩存、格式化、傳輸 |
| 應用程式 Application | 用 Agent 資料做分析、監控、效能評估、預測維護 |

> **⚠️ 易混淆**：OPC UA 可讀可寫、Client/Server、資安內建；MTConnect **唯讀**、XML over HTTP、Device→Adapter→Agent→Application。


:::check 考科一 2.3
某工廠想導入 MTConnect 收集多台發那科（FANUC）CNC 的狀態。在 Device → Adapter → Agent → Application 的資料流中，負責「直接存取控制器資料（例如透過 FOCAS 函式庫），並轉換成 XML 格式」的是哪一個元素？
A. Device
B. Adapter
C. Agent
D. Application
= B
> Adapter（適配器）負責存取設備資料並轉成 XML，不同控制器用不同函式庫（如發那科用 FOCAS）。Agent 是整合多個 Adapter、以 HTTP RESTful API 對外提供的核心；Device 是實體機器；Application 用資料做分析。
:::

## 7. MQTT 深入：角色、主題、機制 {{考科一 2.3｜指引 p.4-59～4-61}}
- 三角色：**發布者（Publisher）**、**訂閱者（Subscriber）**、**中介代理者（Broker）**；以非同步方式傳輸。
- 流程：發布者帶著**主題（Topic）**把訊息送給 Broker → Broker 依主題過濾 → 推播給訂閱該主題的訂閱者。
- 以 Client-Server 來看，**發布者與訂閱者都是 Client**，Broker 是 Server；發布者**不知道**有多少訂閱者。
- **解耦（Decoupled）**：感測器故障，手機 App 不會掛；App 離線，感測器照樣送到 Broker。
- 三個可靠性/安全機制：
  - **Keep Alive**：客戶端定期送訊息維持連線，偵測斷線；Broker 在約定時間的特定倍數內沒收到封包就斷線。
  - **遺囑 LWT（Last Will and Testament）**：裝置**非正常斷線**（沒電、網路斷）時，Broker 代為發送預設的遺囑訊息通知大家。
  - **TLS/SSL**：加密、身分驗證、訊息完整性。
- {{考科一 2.2｜指引 p.4-45 練習題}} **保留訊息（Retained Message）**：發布者可要求 Broker 保留一份最新訊息，給**新加入的訂閱者**立刻收到。


:::check 考科一 2.3
MQTT Broker 需要在裝置「沒有正常斷線、突然消失」時察覺它已離線。下列哪一個機制是讓 Broker 能「偵測」到這種斷線的基礎？
A. Keep Alive：用戶端定期送訊息，Broker 超過約定時間的倍數沒收到封包就判定斷線
B. 保留訊息（Retained Message）
C. 把 QoS 設為 0
D. Topic 使用 # 萬用字元
= A
> Keep Alive 讓客戶端定期送訊息維持連線，Broker 逾時沒收到就斷線，這是偵測非正常斷線的基礎（偵測到之後，若有設定 LWT 才會代發遺囑）。保留訊息是給新訂閱者最新值；QoS 0 是送達等級；# 是訂閱萬用字元。
:::

## 8. MQTT QoS 三等級（必考） {{考科一 2.3｜指引 p.4-61～4-62}}
| QoS | 名稱 | 保證 | 代價 | 適用 |
|---|---|---|---|---|
| 0 | 最多一次 At most once | **不確認、不重傳，可能遺失** | 最省 | 不重要資料、網路良好 |
| 1 | 至少一次 At least once | 等確認，沒收到就重傳 → **保證到達但可能重複** | 中 | 接收方要能處理重複 |
| 2 | 恰好一次 Exactly once | **四步驟握手**，保證只收到一次、不重複 | 最耗資源與時間 | 關鍵訊息（如計費、控制指令） |

> **💡 記法**：0＝「丟了就算」、1＝「一定到，可能兩次」、2＝「剛剛好一次」。**沒有 QoS 3**。QoS 越高越可靠、開銷越大。

## 9. Modbus {{考科一 2.3｜指引 p.4-63～4-65}}
工業設備常用（PLC、溫控器、伺服驅動器），格式簡單；可走串列（RS-232、RS-485）或 TCP/IP。**不支援加密與身分驗證**，在不受信任網路易被監聽、竄改、偽造。**Modbus TCP 常用 502 埠**。採**主從（Master/Slave 或 Client/Server）架構**。

| 模式 | 編碼 | 實體 | 錯誤檢查 |
|---|---|---|---|
| Modbus RTU | **二進制**，效率高 | RS-232／RS-485 | **CRC**（循環冗餘檢查） |
| Modbus ASCII | **ASCII**，可讀性好 | RS-232／RS-485 | **LRC**（縱向冗餘檢查） |
| Modbus TCP/IP | TCP/IP 封裝 | 乙太網路、LAN | 由 TCP 負責；通訊前要建立連線 |

**四種資料區塊**：

| 區塊 | 型態 | 讀寫 | 位址範圍 | 用途 |
|---|---|---|---|---|
| Coil 線圈 | 位元（布林） | **可讀可寫** | 00001–09999 | 控制開/關、繼電器 |
| Discrete Input 離散輸入 | 位元 | **唯讀** | 10001–19999 | 顯示開關狀態 |
| Input Register 輸入暫存器 | 16 位元字 | **唯讀** | 30001–39999 | 讀溫度、壓力等類比值 |
| Holding Register 保持暫存器 | 16 位元字 | **可讀可寫** | 40001–49999 | 類比輸出、設定參數 |

> **💡 記法**：「0 線圈、1 離散、3 輸入、4 保持」；**位元**的是 Coil／Discrete，**16 位元**的是 Register；能寫的只有 **Coil 與 Holding**。


:::check 考科一 2.3
現場工程師希望 Modbus 串列通訊的封包內容「人眼就能直接看懂」，方便除錯，可接受效率較低。應選哪一種模式？它使用哪一種錯誤檢查？
A. Modbus RTU，使用 CRC
B. Modbus ASCII，使用 LRC
C. Modbus TCP，使用 CRC
D. Modbus ASCII，不需要任何錯誤檢查
= B
> Modbus ASCII 以 ASCII 字元編碼，可讀性好、效率較低，錯誤檢查用 LRC；RTU 是二進制、效率高，用 CRC；Modbus TCP 走乙太網路，錯誤檢查由 TCP 負責。
:::

## 10. RESTful API {{考科一 2.3｜指引 p.4-65～4-68}}
基於 HTTP，用 **URL 當資源唯一識別（URI）**，用 HTTP 方法做 **CRUD**；特性：**統一介面**、**客戶端/伺服器端分離**。

| 方法 | 用途 | 常見成功碼 | 常見錯誤碼 |
|---|---|---|---|
| GET | 讀取（Read） | 200 OK | 404 Not Found |
| POST | 建立（Create） | **201 Created** | 400 Bad Request、409 Conflict |
| PUT | 更新或在指定 URI 建立 | 200 OK／201 Created | 404 Not Found |
| DELETE | 刪除 | **204 No Content** | 403 Forbidden、404 Not Found |

開發測試工具：**Mock Server**（模擬後端，讓前後端平行開發，可模擬錯誤、延遲、節流）、**Postman**（模擬 Client，設定參數、標頭、Body，看狀態碼與回應時間、寫測試腳本）。
