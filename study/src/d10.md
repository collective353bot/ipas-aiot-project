## 1. 雲端數據收集與平台架構 {{考科二 2-2｜補充（能力指標 1）}}
| 階段 | 做什麼 | 常見技術 |
|---|---|---|
| 擷取 | 裝置讀取感測值、加上時間戳與裝置 ID | MCU、閘道器 |
| 傳輸 | 送到雲端 | MQTT、HTTP/REST、CoAP、WebSocket |
| 接收 | 接入與驗證裝置 | MQTT Broker、API Gateway、IoT 平台（如 AWS IoT Core、Azure IoT Hub） |
| 處理 | 清洗、轉換、規則判斷、告警；即時串流或批次 | 規則引擎、串流處理、Node-RED |
| 儲存 | 依資料特性選資料庫 | 關聯式、NoSQL、時序資料庫、物件儲存 |
| 應用 | 視覺化、分析、AI、對外 API | Grafana 等儀表板、報表、App |

**平台設計考量**：**可擴充性**（裝置數量成長，水平擴充）、**可靠性**（斷線重傳、資料不遺失）、**即時性**、**資安**（裝置認證、加密、權限）、**成本**（傳輸與儲存費用）、**資料保存政策**（原始資料保留多久、舊資料降採樣彙總）、**裝置管理**（註冊、狀態、OTA）。

> **💡 例子（資料量估算）**：1000 台裝置、每 10 秒上傳一筆、每筆 200 bytes → 每天 1000×8640×200 ≈ 1.7 GB。這類估算決定要不要在邊緣先彙整，以及資料庫與費用的規劃。

## 2. 資料交換格式：JSON、XML、CSV {{考科二 2-2｜補充（能力指標 1：雲端資料交換格式）}}
**JSON（JavaScript Object Notation）**
```json
{
  "deviceId": "TH-001",
  "ts": "2026-10-27T08:30:00+08:00",
  "temp": 26.5,
  "online": true,
  "tags": ["lineA", "zone3"],
  "location": {"lat": 25.03, "lng": 121.56}
}
```
- 物件 `{ }` 由「鍵：值」組成；陣列 `[ ]`；**鍵必須用雙引號**；字串用雙引號（不能用單引號）。
- 值的型別：字串、數字、布林（true／false）、null、物件、陣列。
- **不允許註解、不允許最後一個元素後面多逗號**。

**XML（eXtensible Markup Language）**
```xml
<reading deviceId="TH-001">
  <ts>2026-10-27T08:30:00+08:00</ts>
  <temp unit="C">26.5</temp>
</reading>
```
- 標籤成對、**區分大小寫**、正確巢狀、**只有一個根元素**、屬性值加引號 → 稱為「格式良好（well-formed）」。
- 可用 XSD／DTD 驗證結構；有命名空間；較冗長。

| 比較 | JSON | XML | CSV |
|---|---|---|---|
| 可讀性 | 高、簡潔 | 高但冗長 | 高（表格） |
| 檔案大小 | 小 | 大（標籤重複） | 最小 |
| 結構 | 巢狀物件與陣列 | 樹狀、屬性、命名空間 | 只有平面表格 |
| 結構驗證 | JSON Schema | XSD／DTD | 無標準 |
| 典型用途 | REST API、MQTT 酬載、NoSQL 文件 | 舊系統、設定檔、SOAP、OPC UA／MTConnect 資訊模型 | 匯出報表、批次資料 |

> **⚠️ 易混淆**：JSON 的 `true`、`null` 不加引號；加了引號就變成字串 `"true"`。另有二進位格式（如 **CBOR、Protocol Buffers**）比 JSON 更省頻寬，適合資源受限裝置。

A. CSV 只能表示平面表格，最不適合表達這種巢狀與陣列結構
B. CSV 檔案最小，所以最適合任何結構

## 3. API 與 Topic 設計 {{考科二 2-2｜補充（能力指標 1）}}
**REST API 的 HTTP 方法**（對資源做 CRUD）：

| 方法 | 動作 | 例子 |
|---|---|---|
| GET | 讀取（Read） | `GET /devices/TH-001/readings` |
| POST | 新增（Create） | `POST /devices/TH-001/readings` |
| PUT／PATCH | 整筆更新／部分更新（Update） | `PATCH /devices/TH-001` |
| DELETE | 刪除（Delete） | `DELETE /devices/TH-001` |

**狀態碼**：2xx 成功（200 OK、201 Created）；4xx 用戶端錯誤（400 格式錯誤、401 未認證、403 無權限、404 找不到）；5xx 伺服器錯誤（500、503）。

**MQTT Topic 設計**：用 `/` 分層，從大到小，例如 `factoryA/line1/machine05/temp`；`+` 匹配單一層、`#` 匹配其下所有層（只能放最後）；Topic **區分大小寫**、不要以 `/` 開頭或含空白；**命令與資料分開**（如 `.../cmd` 與 `.../data`）。


:::check 考科二 2-2
某團隊把「雲端下發的控制命令」與「裝置上傳的感測資料」都發布到同一個 Topic `site1/dev01`，結果裝置常把自己上傳的資料誤當成命令。依講義的 Topic 設計原則，最好的改善是？
A. 命令與資料分開，例如 `site1/dev01/cmd` 與 `site1/dev01/data`
B. Topic 改成以 `/` 開頭
C. Topic 中加入空白字元以便閱讀
D. 全部改用 `#` 發布訊息
= A
> 講義的 Topic 設計原則：用 / 由大到小分層、區分大小寫、不要以 / 開頭或含空白，而且「命令與資料分開」。# 是訂閱用的萬用字元，不是拿來發布的主題。
:::

## 4. 關聯式資料庫設計 {{考科二 2-2｜補充（能力指標 1：資料庫設計基礎）}}
- **資料表（Table）**由欄位（Column）與資料列（Row／Record）組成。
- **主鍵（Primary Key, PK）**：唯一識別每一列、不可重複、不可為空值。
- **外鍵（Foreign Key, FK）**：參照另一張表的主鍵，建立關聯並維持**參照完整性**。
- **關聯類型**：一對一、一對多（一台裝置有多筆讀值）、多對多（需中介表）。
- **索引（Index）**：加快查詢，但會增加寫入成本與空間。

**IoT 範例設計**：

| devices | readings |
|---|---|
| **device_id (PK)**、name、location、model | **reading_id (PK)**、device_id (**FK**)、ts、temp、humidity |

**正規化（Normalization）**：減少重複資料與更新異常。

| 正規化 | 要求 | 反例 |
|---|---|---|
| **1NF** | 每個欄位都是**不可再分的單一值**（無重複群組） | 一個欄位存 "26.5,27.0,26.8" |
| **2NF** | 符合 1NF，且非鍵欄位**完全依賴整個主鍵**（消除部分相依） | 主鍵為（訂單號＋產品號），卻存「客戶名稱」只依賴訂單號 |
| **3NF** | 符合 2NF，且**消除遞移相依**（非鍵欄位不依賴其他非鍵欄位） | readings 表裡存 device 的「安裝地點」 |

**基本 SQL**：
```sql
SELECT device_id, AVG(temp) FROM readings
WHERE ts >= '2026-10-27' GROUP BY device_id;
INSERT INTO readings (device_id, ts, temp) VALUES ('TH-001', '2026-10-27 08:30', 26.5);
UPDATE devices SET location = 'B棟' WHERE device_id = 'TH-001';
DELETE FROM readings WHERE ts < '2025-01-01';
```
- SQL 分類：**DDL** 定義結構（CREATE、ALTER、DROP）；**DML** 操作資料（SELECT、INSERT、UPDATE、DELETE）；**DCL** 權限（GRANT、REVOKE）。
- **交易的 ACID**：原子性（全做或全不做）、一致性、隔離性、持久性。

> **⚠️ 易混淆**：`UPDATE`／`DELETE` 忘記加 `WHERE` 會影響整張表。`DROP TABLE` 是刪掉整張表（結構＋資料），`DELETE` 只刪資料列。


:::check 考科二 2-2
DBA 在 readings 表的 `ts`（時間戳）欄位建立索引後，「查詢某段時間的讀值」明顯變快。關於索引，下列敘述何者正確？
A. 索引能加快查詢，但會增加寫入成本與儲存空間
B. 索引能同時讓查詢與寫入都變快，沒有任何代價
C. 索引就是主鍵，一張表只能有一個
D. 建索引會刪除重複資料，等同正規化
= A
> 講義：索引（Index）加快查詢，但會增加寫入成本與空間。索引不等於主鍵；也不是正規化。IoT 寫入量大的表，要衡量索引數量。
:::

## 5. NoSQL 與時序資料庫 {{考科二 2-2｜補充（能力指標 1：資料庫設計基礎）}}
| 類型 | 特性 | 例子 | IoT 用途 |
|---|---|---|---|
| 關聯式 RDBMS | 固定綱要（Schema）、SQL、ACID、JOIN | MySQL、PostgreSQL、SQL Server | 裝置清單、使用者、工單等結構化主資料 |
| 文件型 Document | 存 JSON 類文件、綱要彈性 | MongoDB | 不同型號裝置欄位不一的資料 |
| 鍵值型 Key-Value | 以鍵快速存取 | Redis | 裝置最新狀態、快取、Session |
| 寬欄型 Wide-Column | 大量寫入、水平擴充 | Cassandra、HBase | 海量感測資料 |
| 圖形 Graph | 節點與關係 | Neo4j | 設備拓樸、關聯分析 |
| **時序資料庫 TSDB** | 以**時間戳**為主軸、高速寫入、時間區間查詢、**降採樣**與**保存政策**、壓縮 | InfluxDB、TimescaleDB | **感測讀值、設備監控**（最典型） |

- NoSQL 多數以**水平擴充**與高可用為優先，常採**最終一致性（BASE）**；關聯式重視強一致與 ACID。
- 常見混合設計：**主資料放關聯式、感測讀值放時序資料庫、最新狀態放快取、原始檔案（影像）放物件儲存**。


:::check 考科二 2-2
某平台接入數十種型號的裝置，每種型號上傳的欄位差異很大，而且常常新增欄位。若希望不必每次都修改資料表綱要（Schema），依講義最適合的資料庫類型是？
A. 文件型 NoSQL（如 MongoDB）
B. 固定綱要的關聯式資料庫
C. 圖形資料庫（如 Neo4j）
D. 只用 Excel 試算表
= A
> 文件型資料庫存 JSON 類文件、綱要彈性，講義的 IoT 用途正是「不同型號裝置欄位不一的資料」。關聯式資料庫是固定綱要；圖形資料庫用於設備拓樸與關聯分析。
:::
